# T34 — Read aloud with word highlighting (engine + app)

**Status:** design for approval
**Depends on:** T11 (reading-order text), T21 (test PDFs), T33 (reflow blocks/headings), T38b (reading session), T56 (`/Outlines` reading), T57/T59 (page-fraction navigation patterns)
**Feeds:** T64 (foreground media service wrapping the same controller)

## Goal

The reader taps **Read aloud** and the document is spoken from the current page in
reading order, with the word being spoken highlighted on the page. They can pause,
step a paragraph or a chapter at a time, change the speed, pick a voice, and set a
sleep timer. The position is remembered per document. Everything is offline: only
voices that do not need a network connection are used. Nothing is written into the
PDF.

## Non-goals

- No background playback, notification or lock-screen controls in T34 — that is T64.
  In T34, speech pauses when the app leaves the foreground.
- No OCR. A scanned page with no text layer is reported as "This page has no text
  to read" and speech moves on.
- No description of pictures or tables: they are skipped with a note in the bar.
- No document language detection: the voice's locale is the language, and the
  reader can change it in the system TTS settings (voice picker row).

## Decisions already taken (from the owner)

1. T34 is built first, standalone; T64 wraps it.
2. AndroidX Media3 is approved **for T64**; T34 adds no dependency.
3. Voice selection is Option A: a visible picker (installed offline voices) plus a
   button to the system TTS settings.
4. Chapter/paragraph boundaries are Option C: the PDF outline is authoritative when
   it exists; T33 heading blocks are the fallback.
5. Word highlighting is Option A: per-word on the page, driven by
   `UtteranceProgressListener.onRangeStart` character offsets.

## Architecture

```
engine (pure Kotlin)
  outline/DocumentOutline        reads /Outlines -> title + page + top
  links/DestinationResolver      destination grammar shared with T61
  speech/SpeechModel             SpeechWord / SpeechParagraph / SpeechPage / SpeechChapter
  speech/SpeechExtractor         page -> spoken paragraphs + words + highlight rects; chapters

app
  ui/viewer/speech/SpeechModel   pure navigation: cursors, chapters, sleep timer, speed, voice key
  ui/viewer/speech/ReadAloudController  synchronous state machine over SpeechPageFeed
  ui/viewer/speech/AndroidSpeech  TextToSpeech adapter (+ installed voice list)
  ui/viewer/speech/ReadAloudBar / ReadAloudSheet   Compose UI
  ui/viewer/ViewerViewModel      owns controller + lazy page extraction + action executor
  ui/viewer/ViewerScreen         bar, word highlight layer, auto-scroll, back handling
  data/AppSettings               speech.* keys
  data/ReadingState              speechPage/speechParagraph in the session record
```

### Why the engine owns the text

Spoken text must map exactly back to page rectangles for the word highlight. The
only place that has the page's characters and their boxes is the engine. Building
the word list there keeps the mapping exact and unit-testable on the JVM, and T64's
service then reuses it unchanged.

`SpeechExtractor` runs the T33 `ReflowExtractor` for paragraph and heading
decisions, then works **inside each text block's `pageTextStart..pageTextEnd` range**
of the page layout: tokenise words, compute each word's rectangles with the
existing `PageLayout.rectsFor`, join a hyphenated line break into one word whose
rects span both lines, and build the spoken string ("words joined by one space").
So a page number or footnote dropped by reflow is also never spoken, and every
spoken word has boxes that the app can paint.

### Why the controller is a plain state machine

T64 must run the same playback with the screen off. If playback logic lived in
`ViewerViewModel`, T64 would have to rewrite it. `ReadAloudController` therefore:

- takes `SpeechPageFeed` (already-extracted pages only) and never touches a
  document or a thread;
- returns `List<SpeechAction>` (`Speak`, `Highlight`, `ScrollTo`, `NeedPage`,
  `Paused`, `Finished`, `State`) instead of calling Android;
- is driven by the caller: `onWordStart`/`onUtteranceDone`/`tick` come from the
  adapter, and the caller executes the actions.

In T34 the ViewModel executes the actions and extracts pages on the document
dispatcher. In T64 a service executes the same actions. The JVM tests drive the
controller with fakes, so every navigation rule is covered without a device.

### Reading order and chapters

- Paragraphs: T33 text blocks in reading order (a two-column paper reads down one
  column, then the other; a full-width heading is its own paragraph).
- Chapters: `DocumentOutline.read` entries (title + page + destination top) when
  the document has an outline. Entries deeper than level 2 are kept but not used as
  "next chapter" stops. Without an outline, heading blocks of level 1–2 discovered
  during extraction become chapters, in reading order. This matches the owner's
  Option C.
- `next chapter` = the next chapter after the current position, sorted by
  (page, paragraph). `previous chapter` = the last chapter before it. When the
  current position is inside a chapter, "next chapter" still means the next one
  (like every audiobook player); "previous chapter" first returns to the start of
  the current chapter when the reader is more than one paragraph into it, then the
  previous chapter. This rule is pinned in tests.

### Word highlighting

`TextToSpeech.speak(text, QUEUE_FLUSH, params, utteranceId)` is called once per
paragraph with a stable id `"p:<page>:<paragraph>"`. `onRangeStart(utteranceId,
start, end, frame)` gives a character range in the spoken text; the controller maps
it to the `SpeechWord` whose `start..end` contains `start` and emits `Highlight`.
The app paints `word.rects` through the existing `HighlightOverlay` (a new
`speechRects` parameter) only on the paragraph's page. No polling: a new range
arrives with each word from the engine.

If the TTS engine does not report ranges (some older engines), only the paragraph
is highlighted (its bounds); the bar says "Word highlighting is not available with
this voice" once. This is honest rather than pretending.

### Auto-advance and scrolling

When a paragraph starts, the controller emits `ScrollTo(page, fraction)`; the
viewer scrolls only if the paragraph is not already comfortably visible. When the
last paragraph of a page is done, the controller requests the next page
(`NeedPage`) and waits; the ViewModel extracts it, then calls `onPageReady` and the
controller continues. At the end of the document it emits `Finished` and the bar
shows "Finished".

### Memory

The ViewModel keeps at most three extracted `SpeechPage`s (current, previous, next)
and the controller only ever holds the current paragraph. A 500-page book therefore
holds a few paragraphs of text, not the book.

### Speed, voice, sleep

- Speed presets 0.75×, 1.0×, 1.25×, 1.5×, 2.0× (stored globally).
- Voice: list of installed **offline** voices (`Voice.isNetworkConnectionRequired
  == false`) with engine, locale and name; stored as an encoded key; when the stored
  voice is gone the reader is told and the default voice is used. A "System voice
  settings" button opens `TextToSpeech.Engine.ACTION_ENGINE_SETTINGS`.
- Sleep: Off, end of chapter, 15/30/60 minutes. Minutes are a monotonic countdown
  from when the timer was set; end of chapter pauses when the next paragraph is not
  in the same chapter. Sleep is per session, not remembered.

### Persistence

`ReadingState` gains `speechPage` and `speechParagraph` (defaults 0) as new trailing
fields in the positional record; records from before T34 still decode (the codec
already handles 9- and 10-field records). The position is written whenever the
paragraph changes, so a process kill keeps the spot; T34 does not restore speech
automatically on reopen — the bar offers "Continue reading aloud from page N" once,
which is the same honest behaviour T64 will keep.

### Settings and honesty

A Settings card "Read aloud" holds the default speed, the voice row, and plain
words: "Read aloud uses your device's speech engine. It runs on the CPU, so it uses
battery and can warm the device. Only offline voices are used; PDFPaper never sends
the document anywhere." The bar repeats "Offline voice" and, when a scanned page
turns up, "No text on this page (scan)".

## Acceptance

1. Two-column paper (`t34-paper.pdf`, with an outline): reading order is column 1
   then column 2; the title is not split; the header/page number are not spoken;
   the outline chapters appear in the sheet; the figure is skipped with a note.
2. Book (`t34-book.pdf`, no outline): headings become chapters; next/previous
   chapter work; the sleep timer stops at a chapter end.
3. Word highlighting: the spoken word is highlighted, and the highlight advances;
   on a voice that reports no ranges the paragraph is highlighted and the bar says
   so.
4. Locking/backgrounding the app pauses speech (expected in T34; T64 removes this).
5. The saved position reopens with the same page/paragraph.
6. Screenshots: `t34-reading.png` (bar + word highlight on the paper), `t34-sheet.png`
   (controls), `t34-chapter.png` (chapter list), `t34-voice.png` (voice row).

## Risks / limitations to record in AGENTS.md

- T34 speech stops when the app is not in the foreground (by design; T64 fixes it).
- A scanned page without OCR has nothing to read; the bar says so.
- Pictures and tables are not spoken.
- Word highlighting depends on the TTS engine reporting `onRangeStart`; the
  fallback is paragraph highlighting with an explicit message.
- Chapters from headings are heuristic (T33's rules): a bold 12 pt "Heading 2"
  becomes a chapter; a chapter set in running text is not detected.
- The outline gives chapter titles, not the paragraph to start at; a chapter opens
  at the first paragraph at or below the destination's top.
- The spacing of the spoken text is normalised (single spaces, hyphen joins), so a
  poetry layout or a table read as text loses its line breaks.
- Voice availability is the device's; if the device has no offline voice, Read
  aloud explains that instead of using a network voice.
- Sleep timer "end of chapter" needs a chapter list; with no outline and no
  headings it behaves like Off and says so.
